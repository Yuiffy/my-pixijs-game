# 武侠小说生成器设计说明

## 1. 现状审计

旧版本把 `SNIPPETS` 当作自动滚动的日志源：页面启动后每约 100ms 推进一次事件，玩家只在少数时刻被动点击选项。它缺少开局身份、明确目标、资源压力、可解释的失败、存档和结局复盘，因此“能运行”不等于“值得重开”。

旧世界层还有几处会直接破坏叙事可信度的问题：

- `createWuxiaWorld` 生成 `sect_0` 一类临时 ID，而地图和片段使用 `sect_qingyun` 等真实 ID，主角可能显示为一个门派弟子却站在另一个门派的驻地。
- 世界对象没有稳定的 `turn`、`flags` 和同伴指针，片段读取这些字段时只能得到 `undefined`。
- 结果适配器在 `endGame` 时提前返回，导致同一结果携带的文本、NPC、物品和状态更新丢失。
- `addTurn`、`addExp`、`addMaxHp` 已出现在片段协议中，却没有对应的状态写入。

## 2. 玩法闭环

当前版本采用“短局互动小说 + 轻量资源管理”的闭环：

1. 开局选择出身、执念、姓名和命数种子。
2. 每回合只做一个决定；选择会改变属性、气血、银两、线索、风声、地点和关系。
3. authored beats（关键主线事件）按章节保证出现，generic events 负责填充不同路线的空档；两条同行者事件让关系栏最多容纳两人。
4. 检定使用公开的成功率，失败会给出代价或替代线索，不把玩家锁死在单一路线。
5. 第 12 回合根据执念、线索、名望、侠义、风声和同行者生成结局评分与标签。
6. 本地自动存档；种子可复制，用于复盘和分享同一条命数。

这套节奏把一局控制在约 8--12 分钟：每回合都有决策密度，但不会因为随机事件无限拉长。

## 3. 状态模型

`NovelState` 是可 JSON 序列化的纯数据对象，核心字段如下：

| 类别 | 字段 | 用途 |
| --- | --- | --- |
| 时间 | `turn`, `maxTurns`, `chapter` | 驱动章节和结局时机 |
| 随机 | `seed`, `rngState` | 可复现事件、姓名和检定 |
| 角色 | `hero.stats`, `health`, `silver`, `clues`, `heat` | 形成风险/收益张力 |
| 世界 | `currentLocationId`, `discoveredLocationIds` | 路线和探索反馈 |
| 关系 | `companions`, `affinity` | 让选择产生长期后果 |
| 叙事 | `flags`, `history`, `log`, `currentEvent`, `pendingOutcome` | 解锁条件、回合结算、复盘和存档恢复 |

状态更新集中在 `chooseNovelAction -> applyEffect`，事件构建函数只描述内容和效果。玩家选择后先进入可持久化的 `pendingOutcome` 阶段，保存选择、检定点数、结果段落和实际数值变化；`continueNovelAction` 才会抽取下一事件或生成结局。每次抽到新事件后统一通过 `enterEvent` 同步当前位置与已发现地点，避免正文、横幅和地图各说各话。这种分层让新增事件不必触碰 React 组件，也便于未来把状态机移到服务端。

## 4. 事件扩展协议

新增事件建议遵循以下形状：

```ts
const event = (state: NovelState): NovelEvent => ({
  id: "unique-event-id",
  eyebrow: "第X回 · 标签",
  title: "可被记住的冲突",
  subtitle: "地点 · 氛围",
  locationId: state.currentLocationId,
  mood: "mist",
  lines: [],
  choices: [
    {
      id: "choice-id",
      label: "玩家动作",
      description: "说明代价、机会和长期影响",
      tone: "jade",
      risk: "中",
      preview: [{ label: "线索", value: "+1", tone: "good" }],
      check: { stat: "insight", label: "洞察检定", difficulty: 55, odds: 0 },
      success: { lines: [], effects: { clues: 1 } },
      failure: { lines: [], effects: { health: -10, heat: 8 } },
    },
  ],
});
```

事件选择器应保持三层结构：章节关键事件优先、带条件的支线其次、通用行旅事件兜底。关键事件使用唯一 `id`，通过 `history` 防止同一局重复；条件应读取状态而不是读取 UI。

## 5. 数值与体验原则

- 属性检定公开成功率，范围限制在 18%--92%，让选择仍然有不确定性但不至于无意义。
- 气血低于 30 时提供恢复事件；失败尽量采用“付出代价但保留方向”的 fail-forward 设计。
- 线索上限为 6，避免单项资源无限膨胀；风声上限为 100，用来把高收益选择的风险带回后续事件。
- 结局不只按单一属性判定：执念决定主轴，线索/名望/侠义/风声/同行者共同影响评分和标签。
- 视觉上把资源、风险和当前地点放在同一视野，玩家不必打开说明页才能理解选择。
- 选择结果必须先以独立结算阶段出现；下一事件不能与结果同时抢占视线。结算支持按钮、回车和空格继续，并随自动存档恢复。
- 出身必须同时改变初始数值、归属、出生地和人物形象；镖局是独立归属，不能借用无关门派 ID。

## 6. 存档、分享和兼容

存档键为 `wuxia-novel-save-v1`。写入前只保存纯 JSON 数据，不保存函数或 React 引用。以后升级状态结构时应：

1. 增加版本号，不直接改变旧版本含义。
2. 在读取处做迁移或拒绝不完整数据，并保留“重新开局”路径。
3. 分享链接优先携带 `seed + setup`，而不是整份可变状态；完整存档仍保留本地继续功能。

旧 `WuxiaWorld`/`SnippetResult` 适配层仍可供历史片段和测试使用。它现在使用 `SECTS_DATA` 的真实 ID，提供 `turn/flags/companionId`，并兑现回合、经验、最大气血、死亡标记和结束状态。新 UI 不依赖旧自动播放状态机，后续可逐步把旧片段迁移成上述事件协议。

## 7. 后续扩展路线

### 内容层

- 继续为每个出身增加专属开场；当前第六回盘问已会按门派、游侠和镖局改写场景。
- 把现有雨夜客与负灯医者做成带个人目标的后续关系线，在高亲密度和低亲密度时提供不同事件。
- 增加“门派声望”和阵营关系，使报出师门、卖情报等选择影响后续地点。

### 系统层

- 将事件定义抽成注册表，并加入 schema 校验：唯一 ID、可达地点、预览与效果一致性。
- 增加事件标签冷却和权重配置，做离线可达性检查，确保每种执念至少有一条可完成路线。
- 为结局保存“关键选择时间线”和统计摘要，支持一键复制复盘文本。

### 工程层

- 给 `novelEngine` 增加纯函数单元测试：同种子一致性、资源边界、章节转移、死亡/结局不可重复提交。
- 将存档迁移和事件选择保持为无 DOM 的模块，未来可在 Worker 或服务端复用。
- 在移动端继续采用正文优先布局；新增面板必须不遮挡当前选择，也不能依赖 hover 才能完成核心操作。

## 8. 自动化验收

`pnpm run wuxia:verify` 使用系统 Chrome 覆盖开局、键盘选择、结算停留、回车继续、自动存档、结算阶段刷新恢复、抽屉、12 回合结局、同行者加入、2560x1440 字号下限和 390px 移动布局。脚本还会记录首局的 12 个选择，用相同设置和种子完整重放，逐项比较检定成败、角色资源、同行者、地点和结局。

截图会先做纯色、透明和近黑检查，再人工检查开局、正文、同行者邀约、加入反馈、结局与移动端布局。`window.render_game_to_text()` 同时公开事件地点和当前地点，验收要求两者始终一致。
