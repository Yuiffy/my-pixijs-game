# 自走棋版本与更新日志维护指南

每次合并会改变自走棋玩法、数据、界面、资产或自动化接口的功能时，都要在同一个改动中判断版本号并更新日志。不要把版本维护留到单独的“以后再补”。

## 版本规则

使用语义化版本 `主版本.次版本.修订号`：

- **主版本**：存档、核心循环或外部 AI API 出现不兼容变化。
- **次版本**：新增棋子、系统、回合内容、正式 UI 能力或一批玩家可感知的美术更新。
- **修订号**：不改变现有规则契约的错误修复、小范围平衡和表现修正。

一次改动同时符合多档时，使用最高的一档。纯测试重构、注释和开发脚本整理无需升版本，但仍应在 `progress.md` 记录。

## 必改位置

版本发布改动必须同步以下位置：

1. `package.json` 的 `version`。
2. `src/components/autoChessGame/version.ts` 的 `AUTOCHESS_VERSION`、发布日期和游戏内更新摘要。
3. `CHANGELOG.md` 顶部新增对应版本，日期使用 `YYYY-MM-DD`。
4. `progress.md` 追加实现、平衡依据、验证结果和遗留项。

运行以下命令检查前三处是否一致：

```bash
pnpm autochess:release:check
```

涉及键盘、控制台 API、战斗日志、快速结算或版本弹窗时，在当前源码开发服务器可访问后再运行：

```bash
pnpm autochess:verify:ai
```

脚本默认访问 `http://127.0.0.1:3100`，其他端口通过 `AUTOCHESS_BASE_URL` 指定。它必须使用安装的 Chrome channel，并会拒绝纯色、透明或近黑截图；运行后仍要人工打开 `.tmp/autochess/ai-v<版本号>/` 中的每张截图。

## 更新日志写法

只写玩家、测试者或后续维护者能观察到的结果，不罗列内部重命名。按实际需要使用这些小节：

- `新增`：新系统、新棋子、新入口、新命令。
- `调整`：规则、数值、交互和体验变化。
- `修复`：有明确旧错误和新行为的修复。
- `美术`：生成、替换或重制的资产批次。
- `AI 与测试`：控制接口、日志字段、确定性能力和测试流程变化。

每条应说明“什么变了”和“玩家为什么在意”。平衡调整写出关键旧值、新值或触发条件；兼容性变化必须明确指出。

## 功能改动清单

提交自走棋功能前逐项确认：

- [ ] 判断版本档位，并同步版本源和 `package.json`。
- [ ] 在 `CHANGELOG.md` 未发布版本或新版本下记录玩家可见变化。
- [ ] 游戏内更新日志与根目录日志口径一致。
- [ ] 新键盘操作在 `render_game_to_text().availableActions` 中可发现。
- [ ] 新 AI 操作能通过 `window.autoChessAI` 执行，并返回结构化状态。
- [ ] 新战斗机制补充必要日志，避免只能靠截图猜测。
- [ ] 数据/引擎测试、TypeScript、发布一致性检查通过。
- [ ] 使用仓库的系统 Chrome 流程验证，并人工打开所有证据截图。
- [ ] `progress.md` 记录决策、验证和遗留风险。

## 美术替换清单

生成的新棋子形象先进入 `.tmp/autochess-portraits/<version>/` 审核，不直接覆盖线上文件。确认角色身份和技能职责后：

1. 用纯色键背景生成并执行 `remove_chroma_key.py` 软边缘抠图。
2. 用 `pnpm autochess:portrait:process` 对应脚本归一化为 `512x512` RGBA。
3. 检查四角透明、主体占比、键色残边和小尺寸轮廓。
4. 使用新的语义化文件名发布到 `public/images/autochess/portraits/`。
5. 将单位设为 `portraitStyle: "sprite"`，运行数据测试并在商店、棋盘、战斗和图鉴中查看。

原素材不删除，便于比对和回退。生成提示词、使用的参考图和最终路径应记录在 `progress.md`。
